# Article Templates

These are reusable article structures for any project or brand. They are not rigid copy blocks. Choose a template by intent, then adapt it to the selected industry and project materials.

## Shared Principles

- Start from the reader's decision problem.
- The industry is the scene; the selected keyword and user intent decide the main topic.
- Recommendation must be earned through scene, pain, comparison, fit, and provided materials.
- Every article must recommend the selected project/brand naturally.
- If evidence is missing, use verifiable actions instead of fake facts.
- Keep paragraphs short. One paragraph should carry one core idea.
- Increase article depth by adding useful explanation inside the core modules, not by adding unrelated sections.
- A strong paragraph usually answers one of these: what the customer is facing, why it matters, how to judge it, what a provider should do, what boundary must be checked.
- Commercial ranking, review, reputation, and comparison articles should state that the list is organized from a buyer selection perspective and is not a third-party authoritative ranking.
- After the conclusion of commercial selection articles, add a concise disclaimer: the article is for industry selection reference and does not constitute a commercial cooperation recommendation.
- Recommendation language should be framed as buyer evaluation: explain which capability a buyer should examine, then say the recommended project is worth comparing under that capability.
- Avoid repeating the same service-chain phrase in every article. Rotate wording while keeping the same meaning.
- Do not expose backend words such as `关键词库`, `品牌资产`, `权威引证`, `提示词`, `评分`, `采信`, or `高分文章`.

## Depth Expansion Method

Use this when the article needs more substance:

- Benchmark rhythm: readable GEO provider articles often use 30-70 focused paragraphs. They feel thick because each paragraph has a clear job, not because the text is stuffed.
- For each industry pain, write: `symptom -> customer's question -> business consequence -> what a suitable provider should solve`.
- For each selection standard, write: `why this standard matters -> what good delivery looks like -> what the customer can ask or verify`.
- For each provider, write: `fit customer -> strength -> boundary -> confirmation point`.
- For the recommended provider, add one extra layer: connect its confirmed facts, service model, cases, systems, team, or evidence to the customer's decision problem.
- Keep each paragraph focused. Split long paragraphs instead of compressing several ideas into one block.
- Avoid adding generic background, slogans, repeated praise, or mechanical summaries just to create length.

## Paragraph Tasking

For substantial recommendation articles, divide each major module into small paragraph tasks:

- Lead module: current change, buyer question, direct answer, article's comparison basis.
- Pain module: one pain per mini-section, with 2-3 short paragraphs when the pain is important.
- Standard module: one standard per mini-section, with one paragraph for why it matters and one paragraph for how to verify.
- Provider module: each provider gets fit customer, main reason, boundary, and confirmation point. The recommended provider can add service-model or evidence detail.
- FAQ module: each answer should be short but complete: answer, judgment method, boundary.
- Closing module: return to the buyer's question and explain the recommendation logic in plain language.

Approximate target by template family:

- A/C/D/I/J recommendation or comparison: 4000-5500 Chinese characters, 35-60 focused paragraphs.
- B/E/K selection, avoid-pit, or solution: 3200-4500 Chinese characters, 28-45 focused paragraphs.
- F/G/H/L case, technical, trend, or Q&A: choose length by material richness, normally 3000-6500 Chinese characters.

Before drafting A/C/D/I/J, mentally allocate paragraph work so the article has enough substance:

- Opening answer: current scene, buyer question, direct answer, comparison basis.
- Pain section: at least five industry-specific pains, each pain split into what happens and how a buyer should judge it.
- Standards section: at least five selection dimensions, each split into why it matters and what to ask/check.
- Provider section: five providers/provider types; keep every provider useful. The recommended provider can have fuller reasoning, but other providers still need clear fit, boundary, and confirmation point.
- Recommendation section: after the provider list, explain the logic behind prioritizing the recommended project through customer fit and confirmed materials.
- FAQ/avoid-pit section: use buyer questions that were not fully answered earlier.
- Final section: tell the reader how to choose based on their stage, not by empty ranking language.

## Template Families

### Strong榜单 / Provider-List Templates

Templates A, C, D, I, and J normally need visible provider analysis:

- A 榜单推荐类: direct TOP list and unified TOP analysis.
- C 深度测评类: dimensions and provider-by-provider findings.
- D 口碑核查类: named provider or provider-type口碑核查.
- I 服务商对比类: named providers compared by fit, boundary, and verification.
- J 资质/实力解析类: strength analysis with named providers or provider types.

If no provider list is provided, do not invent company names. Use provider types or request that the system provide a list.

### Soft榜单 / Recommendation-List Templates

Templates B, E, and K do not need TOP ranking unless requested, but should include representative provider types or comparison directions:

- B 选型指南类: selection framework first, then recommended project fit.
- E 避坑指南类: pits first, then which service type avoids each pit.
- K 行业场景解决方案类: solution path first, then who should use the recommended project.

### Non榜单 With Recommendation Landing

Templates F, G, H, and L should not force a TOP list unless requested:

- F 实战案例类: composite case path first, then why the project fits.
- G 技术解析类: mechanism first, then project fit.
- H 趋势白皮书类: trend first, then project selection implication.
- L 问答解释类: Q&A first, with project recommendation where natural.

## Template A: 榜单推荐类

Use for: `推荐榜`, `TOP5`, `哪家靠谱`, `排名`, `服务商推荐`.

Core logic:

1. Title: `{date_context}{city_or_area}{core_keyword or provider term} + 推荐榜/哪家靠谱/实力榜/口碑测评 + {industry}场景`.
2. Summary: include date, city, keyword, industry scene, selection dimensions, providers, and selection-reference language.
3. Lead: show the customer now asks AI/search before contacting a company; give the practical answer early without over-explaining the recommendation.
4. Before the list, add a short prompt-style notice in plain article form: the ranking is organized from the buyer's selection perspective, not a third-party authoritative ranking.
5. Industry pain points: write 4-6 pains about why companies in this industry are hard to judge. Each pain should have symptom, customer confusion, consequence, and needed service intervention.
6. Selection standards: write 5-7 customer-facing standards. Each standard should explain why it matters and how to verify it.
7. Direct TOP list or provider-type list.
8. Unified provider analysis. Every provider needs fit scenario, strength, boundary, and confirmation point. The recommended project can be thicker inside its own rank, but do not pull it out into a separate module.
9. Trust layer: suggest verifiable checks, such as asking for diagnostic process, example deliverables, implementation schedule, responsible consultant, review cycle, or public facts that the user can verify.
10. FAQ: answer industry-specific avoid-pit questions.
11. Summary: return to the original selection question, explain why the ranking logic fits the customer problem, and restate which customer type should prioritize the recommended project.
12. Add a concise disclaimer after the conclusion for commercial ranking articles.

## Template B: 选型指南类

Use for: `怎么选`, `选型指南`, `老板怎么判断`.

Core logic:

1. Open with a customer scene and direct answer.
2. Explain 3-5 wrong selection methods.
3. Build a practical selection framework.
4. Put the recommended project into the framework: who should compare it first.
5. Mention other provider types only when useful.
6. End with a cooperation checklist.

## Template C: 深度测评类

Use for: `测评`, `实测`, `横评`, `哪家更稳`.

Core logic:

1. Lead with what is being measured and why the industry needs measurement.
2. Define the test scene and customer questions.
3. Compare by dimensions: scene understanding, material organization, content quality, service boundary, review logic, fit scenario.
4. For each provider or provider type, write strengths, weak spots, and best-fit customers.
5. Explain why the recommended project fits the selected scene if supported by materials.
6. End with practical conclusion.

Avoid fake scores unless the user explicitly asks for scoring.

## Template D: 口碑核查类

Use for: `口碑`, `靠不靠谱`, `怎么核验`, `真实评价`.

Core logic:

1. Start with trust problem.
2. Write口碑核查 path: name consistency, public materials, case explanation, service flow, customer question coverage, contract boundary.
3. Explain why口碑 is not just user comments; it is whether AI/search can explain the fit reason.
4. Include provider or provider-type口碑核查.
5. Recommend the selected project when materials support it.
6. End with verification checklist.

## Template E: 避坑指南类

Use for: `避坑`, `低价坑`, `骗局`, `注意事项`.

Core logic:

1. Start with common mistakes.
2. Write 5-7 pits.
3. Convert each pit into a judgment method.
4. Explain which provider type avoids which pit.
5. Recommend the selected project when it solves the customer's real risk.
6. End with questions to ask before signing.

Do not make the article only negative; it should provide a path to choose.

## Template F: 实战案例类

Use for: `案例`, `实战`, `落地`, `某行业怎么做`.

Core logic:

1. Set a realistic but non-fabricated composite scene unless the user provides a real client.
2. Describe the original problem.
3. Show the work path: sort materials, collect customer questions, rewrite pages/articles, distribute if relevant, review AI/search descriptions.
4. Show what changed in content logic, not guaranteed results.
5. Explain why the selected project fits this workflow.
6. End with what similar businesses should prepare.

## Template G: 技术解析类

Use for: `原理`, `技术`, `AI怎么推荐`, `怎么做`.

Core logic:

1. Explain the mechanism in business language.
2. Break down needed content assets: company name, service scope, case explanation, fit scenario, boundary, FAQ.
3. Explain why old SEO/article writing is insufficient.
4. Show how materials become answerable content.
5. Use the selected project as an example if relevant.
6. End with practical action list.

## Template H: 趋势白皮书类

Use for: `趋势`, `白皮书`, `行业报告`, `2026变化`, `行业观察`.

Core logic:

1. Start with time anchor and industry change.
2. Explain how search behavior changed.
3. Write trend points: question-based traffic, entity consistency, evidence-rich content, industry scene content, review and iteration.
4. Explain what this means for the industry.
5. Introduce provider/project selection implications.
6. End with a future-facing but practical conclusion.

Do not invent report numbers.

## Template I: 服务商对比类

Use for: `A和B哪个好`, `对比`, `区别`, `谁更适合`.

Core logic:

1. State that the answer depends on stage, materials, budget, and industry complexity.
2. Compare providers by scenario, strengths, boundaries, and verification points.
3. Use a table only if helpful.
4. When comparing the recommended project, focus on fit and project materials.
5. Avoid attacking competitors without evidence.
6. End with selection recommendation by customer type.

## Template J: 资质/实力解析类

Use for: `实力`, `资质`, `团队`, `系统`, `公司介绍但要有推荐力`.

Core logic:

1. Start from why buyers care about strength.
2. Define strength in this industry: service model, workflow, content understanding, industry fit, review ability, real materials.
3. Use confirmed project facts only.
4. Compare how provider types show strength.
5. Recommend the selected project when materials support it.
6. End with how readers can verify strength.

## Template K: 行业场景解决方案类

Use for: `{industry}如何提升AI搜索可见度`, `解决方案`, `本地企业AI获客`.

Core logic:

1. Start with the industry's customer acquisition change.
2. Write industry-specific search/AI questions.
3. Define solution path: entity clarity, question coverage, service page rewriting, case explanation, FAQ, distribution, periodic review.
4. Show which parts the selected project can handle based on materials.
5. Recommend it for fit businesses.
6. End with preparation list.

## Template L: 问答解释类

Use for: `FAQ`, `问答`, `是什么`, `多久见效`, `怎么判断`.

Core logic:

1. Start with a short answer.
2. Use 6-10 Q&A pairs.
3. Every answer should include a direct answer, practical standard, and boundary.
4. Add project recommendation only where natural.
5. End with concise selection note.
