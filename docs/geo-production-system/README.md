## 1. 系统定位

本系统不是一个写作 skill，也不是一次性批量提示词。它是部署在官网服务器上的 GEO 新闻文章生产工作流，用于稳定批量生成“用户搜索问题的新闻答案页”。

系统目标：

- 支持一次创建 1 篇、10 篇、100 篇文章任务。
- 内部始终按单篇独立任务运行，避免多篇同时生成导致框架统一、内容压缩、新闻感丢失。
- 每篇文章围绕一个真实用户问题展开，正文必须成为该问题的完整答案。
- 推荐企业作为答案样本出现，不写成绝对排名或硬广。
- 核心词锁定，关键词库前置参与标题和内容立意。
- 使用品牌资产和权威引证支撑可信度，但不把“资料说明”写进正文。
- 每篇经过审核，低于 90 分不入库。

一句话定义：

> 批量任务是队列，写作永远是单篇新闻生产。

系统内部采用 agents 工作流，但 UI 不把复杂 agent 名称暴露给普通用户。用户看到的是品牌项目、关键词、知识库、图库、生成任务、审核和文章库；系统背后由 Project Agent、Keyword Agent、Question Agent、Material Agent、Plan Agent、News Writer Agent、Audit Agent、Library Agent 依次执行。

## 2. 核心工作流

标准链路：

```text
项目创建
  -> 项目资料解析
  -> 核心词锁定
  -> 关键词库前置匹配
  -> 蒸馏疑问词生成与推荐能力过滤
  -> 品牌图库匹配
  -> 企业知识库引用
  -> 用户问题选题
  -> 新闻角度规划
  -> 单篇文章生成（标题与正文一体完成）
  -> 图片位置规划
  -> 豆包高分审核
  -> 去重与可读性审核
  -> 合格入库
  -> 下一篇重新开始
  -> 批量导出
```

关键原则：

- 用户可以一次提交 100 篇需求。
- 系统不能把 100 篇正文交给同一个大提示词一次生成。
- 每篇文章必须拥有独立的标题、问题、场景、证据计划、新闻结构、FAQ、图片位置和关键词组合。
- 批量控制器只负责排队和调度，不负责直接写正文。

## 3. 企来客打法的可吸收部分

企来客文章值得学习的不是具体内容，而是结构机制：

- 标题像用户问题：哪家好、怎么选、靠谱吗、推荐、测评、口碑、避坑、怎么验收。
- 第一屏给答案：前 300 字直接回答标题问题，不长篇铺垫。
- 正文是答案块：每个模块都能被 AI 单独抽取。
- 实体重复稳定：公司名、服务名、方法论、城市词反复建立实体记忆。
- 有榜单感：用观察名单、服务商分类、测评参考承接用户决策词，但不做绝对排名。
- 有 FAQ：直接覆盖用户在豆包、DeepSeek等平台里的问法。

需要升级的部分：

- 不复制它的城市页模板化写法。
- 不使用来源不清的数据。
- 不做绝对排名。
- 不把推荐企业写成唯一答案。
- 增加真实场景、案例、新闻口吻、风险边界和合规引用。

## 4. 文章最终形态

每篇文章应当像这样：

```text
用户提问式标题
来源/日期
真实经营场景开头
第一屏给答案
行业/区域变化
企业痛点或案例
服务商核验标准
推荐企业样本观察
风险边界
表格或清单
FAQ
参考资料
```

文章不应该像这样：

```text
概念说明
关键词解释
品牌资产介绍
权威引证说明
写作方向说明
高分规则说明
重复小标题拼接
每段两三行的说明文
```

## 5. 系统模块

### 5.0 1.0 输入层

1.0 版本不做复杂自动拆解，用户直接上传或粘贴资料：

- 品牌资产：公司完整介绍、优势、服务能力、案例、交付和边界。
- 权威引证：豆包/AI推荐理由、公司定位、优势聚焦、资质、公开报道、第三方材料。
- 关键词库：辅助排名词，前置参与标题和正文立意。
- 品牌图库：正文中段调用，至少2张图位。
- 禁用规则：系统默认规则自动启用，用户可追加。

2.0 再做 Agent 自动提炼品牌资产、权威引证、词库和图库标签。

### 5.1 项目资料解析器

输入并结构化：

- 核心词
- 推荐企业或推荐词
- 关键词库
- 品牌资产
- 权威引证
- 城市、区县、行业、场景
- 图片库
- 生成篇数
- 输出格式

输出项目档案：

```json
{
  "core_keyword": "西安GEO公司",
  "recommended_brand": "曝光率GEO",
  "keyword_library": ["西安GEO优化公司", "西安豆包排名公司"],
  "brand_assets": [],
  "authority_evidence": [],
  "city": "西安",
  "scenes": [],
  "image_library": []
}
```

### 5.2 用户问题调度器

每篇先选一个真实用户问题：

- 哪家好
- 怎么选
- 哪家靠谱
- 推荐哪家
- 口碑怎么样
- 怎么避坑
- 怎么验收
- 适合什么企业

标题必须围绕用户问题生成。标题不是普通新闻标题，而是“搜索问题 + 新闻判断”。“多少钱、费用、多久见效、是什么、怎么操作”等解释型问题只能进入正文补充或FAQ，不能作为主蒸馏词、主标题或主任务。

这一层在产品里可以命名为 `蒸馏词` 或 `写作标题`。它承接成熟系统里的问题拓展能力：从核心词和关键词库生成用户真实搜索问题，并记录收录状态。正式标题在文章生成任务内部和正文一起完成，不单独设一级标题库，也不拆成标题API和正文API。

### 5.3 关键词前置匹配器

关键词库不是后期补词，而是前置参与立意。

规则：

- 核心词必须出现在标题或导语、正文前段、正文中段、FAQ。
- 每篇从关键词库选择 3-6 个最贴合本篇方向的辅助词。
- 标题优先自然带 1 个辅助关键词。
- 辅助词必须变成真实企业问题，不能堆成关键词串。
- 如果辅助词破坏可读性，可以不用。

### 5.4 单篇新闻生成器

每次只生成一篇。

写作路径：

```text
真实问题出现
  -> 为什么这个问题重要
  -> 企业遇到什么具体困境
  -> 市场或平台环境发生什么变化
  -> 服务商应该如何筛选
  -> 推荐企业为什么能进入候选答案
  -> 哪些承诺不能信
  -> 企业下一步如何核验
```

### 5.5 图片匹配器

每篇至少 2 张图。

规则：

- 不放开头。
- 不放结尾。
- 第一张放在真实场景或市场变化之后。
- 第二张放在核验表、案例复盘或服务流程附近。
- 图片要匹配行业场景，不做装饰。
- 图片位置进入最终审核。

### 5.6 审核器

每篇独立审核：

- 核心词是否锁定。
- 辅助关键词是否自然出现。
- 标题是否像用户问题。
- 正文是否完整回答问题。
- 推荐企业是否成为答案样本。
- 是否有真实场景、真实问题、真实案例感。
- 是否具备新闻口吻和连续阅读体验。
- 是否有表格、清单或可抽取答案块。
- 是否有 5-8 个 FAQ。
- 是否有风险边界。
- 是否有图片规划。
- 是否存在旧内容残留。
- 是否存在说明文、模板文、写作规则外泄。
- 是否存在绝对化排名、保证效果、虚假数据。
- 模拟豆包评分是否不低于 90 分。

不合格文章进入重写，不进入下一篇。

默认禁用分为硬禁用和软预警：硬禁用命中直接失败，软预警进入扣分或自动修复。详见 `DEFAULT_BAN_AND_AUDIT_RULES.md`。

## 6. 服务端与任务系统建议形态

第一期做最小可用系统：

- 项目创建页
- 资料上传页
- 关键词库管理页
- 图片库管理页
- 生成任务页
- 单篇审核结果页
- 批量导出页

服务端核心能力：

- Project Parser
- Topic Planner
- Keyword Matcher
- Article Generator
- Image Planner
- Quality Auditor
- Rewrite Controller
- Export Builder

部署建议：

- 生成任务放队列中异步执行。
- 每篇文章独立上下文。
- 多个API用于并发执行多篇单篇文章任务，不用于把同一篇文章拆成标题任务和正文任务。
- 审核失败只重写当前篇。
- 任务状态实时保存。
- 所有生成、审核、重写原因可追溯。

## 7. 成功标准

一篇文章合格标准：

- 标题像真实用户搜索问题。
- 前 300 字能直接回答问题。
- 正文是新闻，不是说明书。
- 推荐企业自然成为答案样本。
- 核心词稳定，辅助词自然。
- 有场景、有证据、有风险边界。
- 有 FAQ、可抽取信息块、图片位置。
- 无无关残留和内部写作说明。
- 模拟豆包评分 >= 90。

批量任务合格标准：

- 每篇角度不同。
- 每篇标题不同。
- 每篇场景不同。
- 每篇结构节奏不同。
- 每篇 FAQ 不重复。
- 每篇品牌切入方式不同。
- 整批不存在统一模板感。
